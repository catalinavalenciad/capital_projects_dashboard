01 · Project Overview

Background & Motivation

Construction owners managing large capital programs (data centers, hospitals, universities) rely on Project Management Information Systems (PMIS) like Procore, e-Builder, and Oracle Primavera Unifier to track contracts, RFIs, submittals, change orders, and budget performance. But the raw data in those systems is rarely structured for executive reporting without significant analytical work.

This project simulates that analytical layer. Drawing on six years of AEC experience across healthcare, higher education, data centers, and commercial projects, with direct hands-on work in Procore and BIM360, I designed a relational database schema that mirrors real PMIS data structures, generated a synthetic dataset of 10 data center capital projects, and built SQL analytical views and a Tableau dashboard to answer the questions an owner's program management team actually asks.

The project is intentionally framed around the owner's perspective: budget variance, change order trends, RFI response times, and spend tracking: the same metrics that drive capital program decisions.

Tech Stack

  • PostgreSQL: relational database and analytical views
  • Python (pandas, faker): synthetic data generation
  • Tableau Public: interactive dashboard
  • VS Code: development environment
02 · Database Schema

PMIS-Modeled Relational Schema

The schema was designed to reflect how real PMIS platforms structure construction data, not as a flat spreadsheet, but as a set of related tables where every contract, RFI, submittal, and change event traces back to a project. This relational structure enables the kind of cross-table analysis that powers owner dashboards.

All foreign key relationships enforce referential integrity: you cannot log an RFI against a contract that doesn't exist, or a change event against a project that isn't in the system. This mirrors how Procore and e-Builder enforce data consistency.

03 · Data Generation

Synthetic Dataset

No public dataset exists that reflects real PMIS data at the project level because owner data is proprietary by nature. Rather than using a generic dataset, I generated a synthetic capital program using Python's faker library and domain knowledge from six years of AEC practice.

Project locations were chosen based on actual data center market concentration. Dallas, Phoenix, Chicago, Richmond (VA), and others represent genuine tier-1 and tier-2 data center markets. Budget ranges, contract values, RFI volumes, and change order frequencies were calibrated to reflect realistic data center construction programs. The result is 622 rows across six tables that behave like real owner data.

generate_data.py · Python
import pandas as pd
import random
from faker import Faker
from datetime import date, timedelta

fake = Faker()
random.seed(42)
Faker.seed(42)

# Data center market locations: based on real DC market concentration
locations = [
    'Austin, TX', 'Dallas, TX', 'Phoenix, AZ', 'Atlanta, GA',
    'Chicago, IL', 'Seattle, WA', 'Denver, CO', 'Charlotte, NC',
    'Las Vegas, NV', 'Richmond, VA'
]

# Generate 10 projects with realistic budget ranges for data center construction
projects = []
for i in range(1, 11):
    start = fake.date_between(start_date=date(2020, 1, 1), end_date=date(2023, 6, 1))
    end = start + timedelta(days=random.randint(365, 900))
    projects.append({
        'project_id': i,
        'project_name': f'{random.choice(locations).split(",")[0]} Data Center ...',
        'total_budget': round(random.uniform(5000000, 80000000), 2),
        'construction_start': start,
        'substantial_completion': end,
        'status': random.choice(['Active', 'Closed', 'On Hold'])
    })

04 · SQL Analysis

Analytical Queries & Findings

Six analytical views were built on top of the raw tables to answer the questions an owner's program management team would ask. Each view is saved in PostgreSQL and connected directly to Tableau for visualization.

Query 1: Budget Variance by Project

Calculates total actual spend against original approved budget for each project, returning both dollar variance and percentage variance. Projects are ordered from most over budget to most under, giving the owner an immediate read on portfolio health.

SQL · vw_budget_variance
SELECT
    p.project_id,
    p.project_name,
    p.location,
    p.project_manager,
    p.total_budget,
    SUM(bt.actual_spend) AS total_actual_spend,
    SUM(bt.actual_spend) - p.total_budget AS budget_variance,
    ROUND((SUM(bt.actual_spend) - p.total_budget) / p.total_budget * 100, 2)
        AS variance_pct
FROM projects p
JOIN budget_tracking bt ON p.project_id = bt.project_id
GROUP BY p.project_id, p.project_name, p.location, p.project_manager, p.total_budget
ORDER BY budget_variance DESC;

Query 2: Change Order Cost Impact by Project

Aggregates all change events (change orders, CCDs, ASIs, CORs, and field orders) by project to show total cost and schedule impact. High change event volume often signals design coordination issues, unforeseen site conditions, or scope creep, all of which are critical signals for an owner's program team.

SQL · vw_change_order_impact
SELECT
    p.project_id,
    p.project_name,
    COUNT(ce.change_event_id) AS total_change_events,
    SUM(ce.cost_impact) AS total_cost_impact,
    AVG(ce.cost_impact) AS avg_cost_impact,
    SUM(ce.schedule_impact_days) AS total_schedule_impact_days
FROM projects p
JOIN change_events ce ON p.project_id = ce.project_id
GROUP BY p.project_id, p.project_name
ORDER BY total_cost_impact DESC;

Query 3: RFI Volume & Response Time by Project

RFIs are a leading indicator of design coordination quality. High RFI volume suggests incomplete construction documents; slow response times create field delays. This query tracks both dimensions (total RFIs, open vs closed status, and average response time in days) while also flagging how many RFIs escalated into change events.

SQL · vw_rfi_summary
SELECT
    p.project_id,
    p.project_name,
    COUNT(r.rfi_id) AS total_rfis,
    SUM(CASE WHEN r.status = 'Open' THEN 1 ELSE 0 END) AS open_rfis,
    SUM(CASE WHEN r.status = 'Closed' THEN 1 ELSE 0 END) AS closed_rfis,
    SUM(CASE WHEN r.led_to_change_event = TRUE THEN 1 ELSE 0 END) AS led_to_change,
    ROUND(AVG(CASE WHEN r.date_responded IS NOT NULL
        THEN (r.date_responded - r.date_submitted)
        ELSE NULL END), 1) AS avg_response_days
FROM projects p
JOIN rfis r ON p.project_id = r.project_id
GROUP BY p.project_id, p.project_name
ORDER BY total_rfis DESC;

Query 4: Change Event Breakdown by Type & Reason

Breaks down all change events across the portfolio by event type (Change Order, CCD, ASI, COR, Field Order) and reason (Owner Request, Unforeseen Conditions, Design Error, etc.). This cross-tabulation reveals systemic patterns: if Owner Requests are the dominant cost driver, that points to scope management issues; if Design Errors are leading, it points to document quality.

SQL · vw_change_event_breakdown
SELECT
    event_type,
    reason,
    COUNT(*) AS total_events,
    SUM(cost_impact) AS total_cost_impact,
    ROUND(AVG(cost_impact), 2) AS avg_cost_impact
FROM change_events
GROUP BY event_type, reason
ORDER BY total_cost_impact DESC;

Query 5: Submittal Status by Project

Tracks the approval status of submittals (shop drawings, product data, and samples) across the portfolio. Submittal approvals are a prerequisite for procurement and installation; a high rate of "Revise and Resubmit" or "Rejected" status indicates contractor document quality issues that can delay the schedule.

SQL · Submittal Status Detail
SELECT
    project_name,
    'Approved' AS status, approved AS count
FROM vw_submittal_summary
UNION ALL SELECT project_name, 'Approved as Noted', approved_as_noted
    FROM vw_submittal_summary
UNION ALL SELECT project_name, 'Revise and Resubmit', revise_resubmit
    FROM vw_submittal_summary
UNION ALL SELECT project_name, 'Rejected', rejected
    FROM vw_submittal_summary
UNION ALL SELECT project_name, 'Pending', pending
    FROM vw_submittal_summary
ORDER BY project_name, status;

Query 6: Planned vs Actual Spend Over Time

Tracks monthly planned spend against actual spend for the entire portfolio, enabling trend analysis of overall program burn rate. This is the foundational S-curve analysis that owner program managers use to forecast cash flow, anticipate funding needs, and identify months where spending significantly deviated from plan.

SQL · vw_spend_over_time
SELECT
    p.project_name,
    bt.period_date,
    bt.planned_spend,
    bt.actual_spend,
    bt.cumulative_planned,
    bt.cumulative_actual,
    ROUND(bt.cumulative_actual - bt.cumulative_planned, 2) AS cumulative_variance
FROM projects p
JOIN budget_tracking bt ON p.project_id = bt.project_id
ORDER BY p.project_id, bt.period_date;

  • The planned vs actual line chart in Tableau makes the divergence immediately visible without requiring stakeholders to interpret raw numbers.

06 · Conclusion

Key Takeaways

This project demonstrates how construction domain knowledge and data analytics skills can be combined to build the analytical infrastructure that owner organizations need but rarely have. The schema design, data generation approach, SQL analytical layer, and dashboard each reflect real decisions that a data analyst embedded in a capital program management team would make.

The PMIS data model, with its foreign key relationships, change event taxonomy, and submittal workflow, is grounded in how tools like Procore and e-Builder actually structure project data. The analytical questions the SQL addresses are the ones owners are actually asking: where are we over budget, what is driving our change orders, are our RFIs getting resolved, and how is spend tracking against plan?
